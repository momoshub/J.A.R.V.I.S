# CLAUDE.md

Guidance for working on this repo. Keep it accurate - update it when behavior, structure, or conventions change.

## What this is

A configurable Slack agent bot (Bun + TypeScript). Its "brain" is the local **Claude Code CLI** (default) or the Anthropic API. It has SQLite memory, an allowlist with roles, live streaming replies, a command registry, and a React admin dashboard. The code is **generic** - the running instance's identity (name, persona, prefixes, etc.) lives in the DB / env, never hardcoded.

## Commands

```bash
bun test              # full test suite (bun:test)
bun run typecheck     # tsc --noEmit  (root)
bun run build:web     # build the React dashboard (web/ -> web/dist)
bun start             # run the bot + dashboard
bun run setup         # install + build:web
```

Always run `bun run typecheck` AND `bun test` before considering a change done. The `web/` app has its own `tsconfig`/deps - typecheck it with `cd web && bunx tsc --noEmit` after touching it, and rebuild (`bun run build:web`) since the bot serves `web/dist`. CI typechecks and builds `web/` too. `web/dist` is not committed and is read per request, so after a web-only merge run `bun run build:web` in the main folder - no restart needed.

## Architecture (clean, layered - dependencies point inward)

- Two processes: `src/gateway.ts` holds the Slack socket and writes every envelope to `data/inbox.db`, and never restarts; `src/index.ts` is the bot (`SLACK_TRANSPORT=inbox`), reads the inbox, runs one turn per thread on its own `claude --resume` session, and is the one that restarts
- `src/domain` - pure logic, no I/O: `types`, `access` + `toolPolicy` + `rolePolicy` (roles), `slackNames` (name + id labels), `conversation`, `mentions`, `personality`, `inbox`, `connectionHealth`, `offlineAlarm`, `watch`/`reminder`/`selfUpdate`/`runControl`, `*Prompt` (preset tasks), `blockKit`/`slackFormat`/`slackLinks`, `promptGuides` (on-demand prompt blocks), `adapter` + `adapterCheck` (memory), `githubApp` (webhook triggers)
- `src/application` - use cases + ports: `ports` (`LlmPort`), `respond`, `handleMessage`, `commands` + `commandTickets` + `commandLimits` + `brainRun`, `threadQueue` + `runRegistry`, the timers (`watcher`, `reminders`, `reviewInbox`, `reviewGuard`, `innerChild`, `offlineAlarm`), `githubApp` (webhook calls), `workflow*`, `accessRequests`, `adapterMemory`, `botProfile`, `slackAdmin`, `draftReply`, `dashboard` (every dashboard read and write; the server only parses and maps), `rolePolicies` (the policy-enforced allowlist), `nameResolver` (cached Slack names for the dashboard)
- `src/infrastructure` - adapters: `slack/*` (`gateway`, `inboxReceiver`, `app`, `stream`, `adminClient`, `offlineAlarmClient`), `inbox/inboxRepo`, `db/*` (bun:sqlite repos + schema/migration), `llm/claudeCli` + `llm/anthropic`, `github/*` (incl. the GitHub App's `appClient`/`appCredentials`/`webhookServer`), `system/*` (host probes, `guideWriter`), `dashboard/server`, `adapter/adapterStore`
- `src/config/env.ts` - zod-validated env, fails fast
- Composition roots: `src/index.ts` wires the bot, `src/gateway.ts` reads only `SLACK_APP_TOKEN` + the inbox path so a new bot setting can never stop the gateway from starting
- `web/` - React 19 + Vite + React Router 7 dashboard (`react-router` package, not `react-router-dom`; Claude-style theme, colours only via the CSS variables in `styles.css`, dark is ONE block keyed on `<html data-theme="dark">` - the resolved value, set before paint by `public/theme-init.js` (a file: the CSP refuses inline scripts) and kept by `ui/theme.ts` (system/light/dark, same `THEME_KEY`, a test holds the two together); JSON API under `/api`). `web/src`: `main.tsx` mounts, `routes/router.tsx` is the route table only, each `pages/*.tsx` owns its loader + action + component, `ui/` holds the shell and shared bits, `api.ts` is the only place that fetches
- Full docs: `README.md`, `ARCHITECTURE.md`, and the dashboard's Architecture page (`web/src/systemModel.ts`: boxes, wires, playable request flows). When the runtime shape changes, update that model in the same PR - `tests/web/systemModel.test.ts` fails on a flow naming a missing box or wire, a source path that no longer exists, an unexplained wire, or a wire drawn through a box. The static System design sections under it come from `web/src/systemDesign.ts`; `tests/web/systemDesign.test.ts` fails when a drawn table or column is not in the schema, a limit no longer equals the constant it cites, or a deployment link crosses a box - so a schema change, a constant change or a new runtime piece updates that file in the same PR

## Conventions

- **TypeScript, functional style. No classes** - repos/adapters are factory functions returning a bag of functions. Do not introduce OOP.
- **Never use `any`.** Use precise types; `unknown` + narrowing at boundaries.
- Local imports use explicit `.ts` extensions (Bun style).
- Use `bun:sqlite`; SQL is parameterized (named/positional binds), never string-concatenated.
- Depend on ports (`LlmPort`, `SlackAdminPort`, injected clocks/deps), not concrete adapters, so use cases stay testable with fakes + `:memory:` sqlite.
- Keep changes small and focused; add/adjust tests with any behavior change (TDD).

## Key facts (non-obvious)

- **Identity is data, not code.** Bot name/persona/labels live in the DB `settings` table (seeded, editable from the dashboard). Command triggers (`COMMAND_PREFIX`, `SLASH_COMMAND`), model, cwd, owner id, etc. come from env. Do NOT hardcode instance-specific strings (bot name, command prefix, db filename) in `src/` - the code defaults are neutral (`Assistant`, `//bot`, `data/bot.db`) and each instance overrides via env + DB.
- **The DB is committed** (path from `DATABASE_PATH`) and carries the allowlist + identity. Conversation `messages` are cleared before committing; WAL sidecars are gitignored. After schema changes, migrations run via `PRAGMA user_version` in `db/schema.ts`.
- **`ALWAYS_DISALLOW`** (`domain/toolPolicy.ts`) is denied to every role including full access - `--disallowedTools` is honoured alongside `--dangerously-skip-permissions` (verified), so it is a real denial. It holds the Slack connector's **write** tools by name (`SLACK_CONNECTOR_WRITES`: send/schedule/draft/canvas) and CloudWatch. It used to ban the connector wholesale, which also refused the READS - and reading impersonates nobody; it is the only way to see a channel or group DM the bot was never invited to. Posting is the thing that arrives under the authorising human's name, so only that is denied.
- **Roles** (`src/domain/access.ts`, `toolPolicy.ts`): `pal` < `executer` < `admin` < `owner`. owner/admin run the CLI full-access; pal/executer are sandboxed (`--allowedTools` allow-list, no `--dangerously-skip-permissions`, fixed cwd). `review` is a preset that always runs full-access and writes to the PR.
- **Role policies are restrict-only, and enforced where the allowlist is read** (`domain/rolePolicy.ts`, `application/rolePolicies.ts`, `db/rolePolicyRepo.ts`, migration v24 `role_policies`, dashboard Roles page): the owner asked for roles to be switched on/off and given command/tool/MCP permissions from the dashboard. The four roles and every ceiling stay in code - a command's `minRole`, `SANDBOX_DISALLOW`, the DB servers - because those carry reasons a checkbox must not undo (a `watch` predicate is shell, a DB server is production), so a policy can only TAKE AWAY: switch a role off, deny commands within its rank, deny tools and whole MCP servers. Enforcement is three seams, not N call sites: `index.ts` wraps the user repo with `enforceRolePolicies`, so a member of a switched-off role is simply not on the allowlist for every `users.get`/`list` in the bot (chat, commands, buttons, the run bridge, the review inbox and GitHub App name matching); `dispatchCommand` refuses `deniedCommands(role)` after the `minRole` gate and `help`/the menu/near-miss suggestions leave them out; `toolPolicyFor`'s `roleDisallow` appends denied tools and `mcp__<server>` to `--disallowedTools` for that role (a denial is the only lever that refuses - see the allow-list note). A disabled member is told their role is off (`roleDisabled` -> `disabledRoleReason`) rather than raised to the owner as an access request. The owner role is always on and never restricted whatever row is stored (`effectivePolicy`), and the dashboard refuses to save one, so no save can lock the owner out; presets that run as `toolPolicy("owner")` (`adapter refine`, `close`, `note`, ...) are therefore untouched - deny the command to keep a role off one. `help` cannot be denied. Two readers keep the RAW repo, because they must see and fix members of a switched-off role: the dashboard, and the commands that manage people (`rawUsers` on `CommandDeps`: `add`/`remove`/`promote`/`demote`/`users`/`snub` targets - with the enforced view `remove` said "not on the list" and `add` overwrote the record against an assumed `pal`); the ACTOR is always read enforced. A watch is gated too (`mayRun` on the watcher, the enforced allowlist plus the owner): its predicate is shell run as the bot, so a switched-off or removed setter's watch is settled `failed` with one line before the predicate runs, never after. Read per call (a PK SELECT), so a save applies on the next message with no restart.
- **The dashboard never shows a bare Slack id** (`domain/slackNames.ts`, `application/nameResolver.ts`, `conversationInfo` on `SlackAdminPort`): Conversations, a conversation's turns (authors and `<@U…>` mentions in the content), the command log and Spend all show `Name (U…)` and `#channel (C…)` / `@Person (D…)`; an unresolved name reads `unknown (U…)`, never the id twice. Names come from `conversations.info` / `users.info` through ONE resolver per dashboard process that caches answers 6h and failures 10 min and shares in-flight lookups, so opening a page with forty rows is not forty Slack calls; a name stored on the allowlist wins and costs no call. The Users page edits Slack id (a rename also moves the person's GitHub links), Slack name (refreshed from Slack when they next write - `ensureUserRecord`), GitHub logins and role. GitHub logins are NOT a new column: they are the existing `github_login:<login>` -> Slack id settings that `slackIdOfGithub` already reads, because two stores of one mapping means one of them is lying; a login linked to someone else ON the allowlist is refused, not stolen, while a link held by someone no longer on it is stale and free to take; removing a user drops their links. Role input is refused unless it is admin/executer/pal - never a silent fallback to `pal`, which is a demotion nobody asked for. Cold renders look up at most `NAME_LOOKUP_CONCURRENCY` (5) conversations at once, so a long list does not trip Slack's rate limit.
- **Turn timeouts**: a chat turn is killed by `CLAUDE_TIMEOUT_MS` (this instance: 50 min; code default 120s), which surfaces as `claude CLI exited with code 143: no output`. `isTimeout()` tells that apart from a real failure so the thread says "ran past my time limit, narrow it or use `workflow`" instead of "I hit an error" - the generic apology reads as a bug and invites the same expensive question again. Investigation turns (gcx/VictoriaLogs loops) are what hit it.
- **UI access probe** (`domain/uiAccess.ts`, `infrastructure/system/uiAccessProbe.ts`): macOS Accessibility is granted against the *path* of the launching binary, so for this launchd agent it is the runtime (`/opt/homebrew/bin/bun`), not `claude` and not a terminal - and an interactive test passes while the bot still cannot, because the terminal has its own grant. Worse, a package upgrade moves the binary and the grant silently stops matching (bun is `brew pin`ned here for that reason). So it is probed with `AXIsProcessTrusted()` (~50ms, cached 5 min), logged at boot, and reported on `/health` as `ui`/`uiState`. NOT by scripting System Events, which was the first attempt and answers a different question - Apple Events/Automation, grantable while Accessibility is not - so it reported `allowed` while the real UI call was refused. Note the probe reports on the BOT process; the brain's UI actions run inside the spawned CLI, which the system may hold responsible instead, so a denial names both binary paths. It never touches `ok`: nothing core needs the UI, which is precisely why losing it goes unnoticed. A probe that fails for a non-permission reason reads `unknown`, never `denied`.
- **Slack listening is a separate process** (`src/gateway.ts`, `infrastructure/slack/gateway.ts`, `infrastructure/inbox/inboxRepo.ts`, `slack/inboxReceiver.ts`, `domain/inbox.ts`): every restart to pick up a code change used to drop the socket, and whatever Slack sent in that window was gone. With `SLACK_TRANSPORT=inbox` a small gateway holds Socket Mode, writes each envelope to `data/inbox.db` (its own gitignored SQLite file, WAL, two writers) and acks; the bot reads that queue through a custom Bolt `Receiver`, so every listener in `app.ts` runs unchanged - same say/respond/client. Stored BEFORE acked, so an ack always means "we have it"; a failed write is left unacked so Slack retries. Dedupe is on `event_id` (Slack retries under a new envelope id). Events ack at once; interactive and slash envelopes wait up to `ACK_WAIT_MS` (2.5s) for the bot's own ack and pass its payload through, because a modal's `response_action: errors` lives there - a bot that is down gets an empty ack and handles the row when it is back (a `trigger_id` is dead by then, a `response_url` is not). Rows run `pending -> running -> done|failed`; on boot `recover` retries a `running` row by itself: at once after the first cut-off, then `RETRY_DELAY_MS` (5 min, via `not_before`) after each later one, up to `MAX_ATTEMPTS` (4). The delay is there because a second cut-off usually means something is still going on - a git operation swapping `data/jarvis.db` out was the real case, crashing the bot twice on one message - and the cap is what keeps a message that crashes it every time from becoming a crash loop. Asking a human after the second cut-off was the first version, and the owner rightly said it should just pick itself back up. Age counts from the last attempt (15 min), not arrival, so a message still being worked on is never "too old"; `pending` rows older than a day are dropped, since a reply hours late reads as a malfunction. The restart idle check counts envelopes in flight as well as runs, and a pending restart stops claiming new rows. The socket watchdog moved WITH the socket: the gateway exits itself when deaf, while the bot reads health from the gateway's heartbeat row (stale after 30s counts as disconnected) and never exits over it, since restarting the bot cannot fix the gateway's socket. Never run both transports at once for long - Slack load-balances events across connections, so a socket-mode bot plus a gateway each see only part of the traffic. `socket` stays the code default so an instance with no gateway is unchanged.
- **A reply cut off mid-stream is tidied and the retry is told** (`addStream`, `tidyInterrupted`, `interruptedRules`): a graceful restart rarely cuts a stream (it waits for idle, up to `RESTART_MAX_WAIT_MS`), but a forced one, a crash or `kickstart -k` did, leaving a half-written message still marked streaming and a redelivered row that read the request as brand new - a second branch, a second PR. Now every message a row's reply opens is recorded on the row (`onOpen` in `slack/stream.ts`), and on boot `recover` reports them: each is `chat.stopStream`ed, the first is rewritten with `interruptedNotice` and any rollover continuations deleted, BEFORE any row is handed out so the retry's answer lands below the notice. Measured against the real API: a stream orphaned by a dead process CAN be stopped from a fresh one, and the rewrite must carry a `markdown` block - a `context`-only rewrite of a stopped stream is refused with `block_mismatch`. The retry gets `inboxAttempt` through Bolt's `customProperties` -> `context`, and attempt > 1 adds `interruptedRules` to its prompt: check what the first attempt already did and continue rather than repeat. That block is per-turn and not in the prompt fingerprint's sentinels, so it never resets the thread's session - which is the point, the session is where the first attempt's tool calls are.
- **Connection watchdog** (`domain/connectionHealth.ts`, wired in `slack/app.ts`): Socket Mode goes deaf silently - process up, launchd happy, dashboard answering, no messages arriving. `KeepAlive` only revives a process that exits, so the app exits itself (`process.exit(1)`) when the socket has been away longer than `CONNECTION_GRACE_MS` (3 min). `reconnecting` counts as away: both real outages were spent entirely in reconnect attempts. `/health` reports the socket state and 503s when deaf, because "recent activity" cannot distinguish quiet from deaf - that mistake was made twice.
- **Slack's own stop button** (`domain/agentSession.ts`, `agent_session_stopped` in `slack/app.ts`): a thread the bot streams into is an *agent session* to Slack, and Slack draws the controls. Subscribing to this event is what makes the spinner an interactive stop button - WITHOUT the subscription Slack shows a loading indicator nobody can press, which looks like a control and does nothing. A press owes two things, and the second is the one easy to miss: stop the work, AND close every ts in `streaming_message_ts` with `chat.stopStream`, or the session stays in `processing` with no way out. The streams are closed even when nothing was running, for exactly that reason. The thread key comes from `sessionThreadKey`, which `respond` now also calls - if the two ever built that string differently the button would silently find nothing to stop and only the spinner would say so. Deliberately NOT gated by the "your own turn, or an admin" rule that guards the bot's own stop button: that rule is right for a button the bot drew, but this one is Slack's, shown to anyone who can see the session, and an agent that leaves the platform's own affordance inert is broken. A press is honoured and the notice names whose turn it was when it was not the presser's. Scopes needed are `chat:write` + `assistant:write`, both already granted here; the event subscription is app config at api.slack.com and cannot be set from code.
- **Stopping a turn kills the TREE, and says so honestly** (`infrastructure/llm/killTree.ts`): `proc.kill()` signals only the CLI, but the model's shell commands are its children - measured here, after `proc.kill()` on a shell waiting on children the parent's exit code was still `null` and two grandchildren were orphaned. Worse, a wedged CLI ignores SIGTERM outright: a stuck turn was found at 26 minutes, 0% CPU, no children, having shrugged off four stop presses, and only died on SIGKILL. So `stopProcess` SIGTERMs the whole tree (children collected BEFORE the parent, or they reparent to init and cannot be found), then SIGKILLs anything still standing after `KILL_GRACE_MS`. Separately, `stopping` is now its own `RunState`: a stop is a REQUEST, and a registry that cannot tell "asked to stop" from "running" reports a fresh successful stop on every press - four presses produced four confident "stopped" lines while nothing died, which is worse than having no button.
- **A sink that throws must never abandon the CLI's stdout** (`claudeCli.stream`): the sink posts to Slack and Slack fails - `msg_too_long` alone appears dozens of times in the log. A throw out of the read loop left the child's stdout undrained, and a pipe nobody reads fills at ~64KB and blocks the writer FOREVER: 0% CPU, alive, unkillable by SIGTERM. That is what the wedged turn above actually was. Every emit is now wrapped (sync throw and rejected promise both), and the loop has a `finally` that releases the reader plus a `catch` that reaps the child, so a turn can never outlive its own stream call.
- **Stopping a turn** (`application/runRegistry.ts`, `domain/runControl.ts`): every chat/workflow turn is tracked with an `AbortController`; the signal reaches `claudeCli`, which kills the child (same kill as the timeout, so a stopped run surfaces as exit 143 and `respond` must check `signal.aborted` before reporting it as a timeout). The busy notice is now interactive - `STOP_ACTION` ends the running turn, `DROP_ACTION` takes the just-queued one back before it spawns - and `stop` does the same without a new message. `decideRunPress` holds the rule: your own turn, or admin. A button whose run already finished answers "gone" rather than erroring.
- **The owner moves its messages with a reaction** (`application/messageReactions.ts`, wired in `slack/app.ts` `reaction_added`): 🚼 `baby_symbol` flips a thread reply to "also send to channel" (`chat.update` `reply_broadcast`), 🧱 `bricks` takes a broadcast reply back into the thread only, `sausage_punch` deletes. `bricks` is `chat.delete` with `broadcast_delete: true` - undocumented, captured from the Slack client's "Remove from channel", works with the bot token: the channel copy goes, the thread reply keeps its ts. `chat.update` with `reply_broadcast: false` returns ok and does nothing. Owner only, and only on messages the bot wrote; anything else is ignored and logged. Replies never broadcast on their own, not even the first one in a thread the bot opened: sending one to the channel is always this reaction.
- **Every tool call is logged in full, one file per thread** (`infrastructure/llm/toolTraceLog.ts`, `onToolTrace` in `claudeCli`): the Slack cards are clipped to a line and then collapsed away when the turn ends, so afterwards nothing showed what a turn actually ran or what came back. `claudeCli.stream` now reports every call (full input JSON, plumbing tools included) and every result (full output), plus a subagent's own steps with `parent` set to the Task call that spawned them, and the composition root appends them to `<LOG_DIR>/threads/<channel>/<threadTs>.jsonl`. The thread comes from `BillingContext.threadTs`, set by chat (`threadTs ?? messageTs`), workflows and every command that spawns a brain; a run with no channel lands in `_none/<date>.jsonl`. Secrets are redacted with `redactSecrets`, each field is clipped at 100k chars, path parts are sanitised, and a sink that throws can never take the run down. `complete()` goes through the stream-json path too whenever a trace sink is wired (`completeTraced`), keeping its contract - throw on a non-zero exit or an error result - because the one-shot json output carries only the final answer and left no record of what ran.
- **A bundled question is split and answered as it lands** (`SPLIT_QUESTION_RULES` in `domain/personality.ts`, inline or as the `parallel` guide - see the how-to guides entry): a message carrying several asks used to be worked through in one line, so the quick part sat unread until the slowest one finished. The rule tells the turn to split the message, run the independent parts in parallel as background agents - always Orca workers (a fresh `run-create` per batch since the bound Run is shared by every thread, `worker-start --run`, done when every task in `task-list --run` is completed or failed - a running one is `dispatched` - checked by a deadline-bound background loop or a watch since Orca cannot wake a `claude -p` turn, results read with `inbox --full`; the Agent tool only when the Orca runtime is down or the role cannot run `orca`; the same lines live in `ORCA_AGENT_RULES`, which the workflow worker prompt also carries, and a multi-agent workflow runs its agents as Orca workers rather than through the Workflow tool, waiting for a batch across steps with the carry-on line and at most a 5-minute foreground loop per step, never a watch since a watch turn lands on the front, and never bare check steps, which burn the auto-continue cap) - and post the first finished part with `chat.postMessage` then fold later parts into that same message with `chat.update`, so the thread gets one message that fills in. Parts that consume an earlier answer still chain, and a single question is answered the normal way. It is in the prompt fingerprint, so live threads pick it up.
- **It follows a thread it started** (`domain/threadFollow.ts`, wired in `slack/app.ts`): it used to answer exactly two things, a DM and an @-mention. Right for a channel it is a guest in, wrong for a thread it OPENED - it posts a summary, people reply underneath discussing it, and it sits there deaf unless somebody remembers to tag it. A reply under a thread whose PARENT it posted is now treated as addressed to it. Ownership is the parent's author and nothing else: being mentioned earlier in a thread, or having replied in one, does not make the thread its own, or a single tag in a busy channel would sign it up to narrate the rest of the day. A tagged message is skipped here because `app_mention` already has it - following it too answers the same message twice. The parent's author is cached per thread (one lookup, not one per message; failures cached too, since retrying on every line of an unreadable thread is a loop, not a recovery). `follow_own_threads=off` turns it off. Following without judgement is just noise, so a turn that arrives this way carries `following: true` and gets `followRules` (`personality.ts`): most replies under its own thread do not need it, two people working something out do not want a third voice agreeing, a REACTION is usually the right size of response, it may ask at most ONE question and never for something it could look up - and silence is an explicit outcome. An empty reply posts nothing (`respond` only posts `result.text.trim()`), which is correct and common here - and the rule now forbids ANNOUNCING the silence by name, because the first thing it did with the permission was post "I'm staying quiet here: ... a reaction is enough" into a public channel. A message whose entire content is the decision not to send a message is worse than simply answering: it spends the room's attention on the bot's own reasoning. The test given is "if the only content of your reply is about whether to reply, send nothing instead". The queue notice is suppressed for the same reason - "still working on X, yours is next" is the bot talking about its own scheduling in a thread nobody summoned it to. The thinking placeholder is also NOT armed when following: nobody asked, so nobody is waiting, and a "burning token" card in a channel announces a turn that may well say nothing. The rule is in the prompt fingerprint, so live threads pick up changes to it.
- **A thread it did not start can be opted in** (`follow` command, `db/followRepo.ts`, migration v15, `shouldFollowThread`): following was ownership and nothing else, which is the right default for a room the bot is a guest in and is NOT what anyone means by "auto reply to this thread" - they are pointing at a conversation a person started and asking it to keep up without being tagged on every line. Asked for exactly that twice, it answered "I can't auto-reply to every message in a thread", which was true and useless. `follow` (in the thread, or with a link) adds a row; `follow off` removes it; `follow list` shows them. Membership is checked on every untagged message in every thread the bot can see, so the repo keeps it in a `Set` refreshed on write rather than doing a SELECT per line for an answer that changes twice a week. An explicit follow OUTRANKS `follow_own_threads=off`: that setting governs the blanket default, and somebody who turns the default off and then points at one conversation means what they said. The parent-author lookup is now skipped whenever the answer cannot depend on it, which also takes a Slack call off the hot path. admin+, because it makes the bot speak in a shared room without being spoken to. `followRules` no longer says "a thread you started" - a rule that tells it it opened a conversation it did not open is a rule it will argue with - and everything else about it is unchanged, so silence is still the common outcome.
- **A thread that is just it and one person is followed, always** (`isOneOnOneThread`): someone who tagged it once and keeps talking with nobody else in the thread is still talking TO it, and making them tag it on every line is friction for nothing. It needs the bot to have written in the thread (so an untouched thread is never claimed) and exactly one human, the current author counted even before Slack lists them; a second person ends it. Participants come from the parent's `reply_users` in the same `conversations.replies` call that gives the parent's author, cached 30s rather than forever because unlike the author they change. Not gated by `follow_own_threads`, which is about threads it opened.
- **Background work that dies with the run is named in the reply** (`backgroundCutOffNotice`, `claudeCli.stream`): a turn may start a sub-agent or shell with `run_in_background` and end its answer. The CLI then lingers for those tasks, so the run stays tracked and a self-restart correctly waits - but only for a grace period (measured: exactly 10 minutes after the answer), after which the CLI kills them and exits. Nothing said so; a long backend job just stopped and the owner had to ask "???". The CLI reports its live list in `system/background_tasks_changed` events, and whatever is still on it at exit is appended to the reply (streamed, and in the returned text for a dead-stream rewrite) with each task named.
- **Thread queue** (`application/threadQueue.ts`, wired in `respond`): chat and workflow turns of one thread run strictly one at a time. Two messages minutes apart used to run concurrently and each complete the same task (two branches, two PRs) while both resumed the SAME session id from two processes. Commands are intentionally not queued (own process, own session). A failed turn never breaks the chain behind it; `depth()` lets the thread be told it is waiting.
- **Thread sessions** (`domain/threadSession.ts`, `db/threadSessionRepo.ts`): every Slack thread gets ONE CLI session - first turn `--session-id`, later turns `--resume` - so the model keeps its context between turns and a resumed turn is handed only `unseenTurns()` (everything said since its last turn), not the thread replayed. Keyed by (channel, thread, **tier**): full-access and sandboxed roles use different cwds and the CLI files a session under the cwd it ran in, so cross-tier resume is impossible anyway and sharing would leak a full-access session's reads to a pal. The session is claimed BEFORE the run, never after: a turn that dies is usually the long one, and leaving nothing bound makes the retry start cold and repeat the discovery that ran it out of time. `isMissingSession()` (`No conversation found with session ID`, verified against the CLI) means silently mint a new session and replay the thread cold; any other error still throws. Setting `thread_sessions=off` and the `session` command turn it off / reset one thread.

The owner made a second reader mandatory: after the PR is open, a separate agent with fresh context reads the diff cold (correctness, regressions, missing tests, stale docs), never as a fork (that inherits the writer's context). It is an Orca worker like every other background agent (the owner's call: it used to be a background Agent-tool agent talked to over SendMessage, which never showed on Orca), in a fresh Run, falling back to a background Agent only when Orca is unreachable or the tools refuse `orca`. The two talk only on the PR: the reviewer posts each round as a PR comment opening with `[review round N]` and ending `VERDICT: clean|changes`, the writer pushes and answers with a `[fix round N]` comment, and the reviewer polls the PR, re-reads the new head and exits on a clean verdict, after round 3, when the PR is merged or closed, or after 40 minutes with no fix comment - so nothing is left to stop with TaskStop. It reads through `gh` only and never checks out in the folder Orca starts it in (usually a live shared checkout), cutting its own worktree if it must run the checks. The markers tell the sides apart even on one GitHub account. With `SELF_PR_AUTHOR` and `SELF_PR_REVIEWER` both set (owner's rule, `selfPrAccountsRule`, appended to both self-update blocks and the inner child's `fixPrompt`), the PR and the `[fix round N]` comments go out as the author and the `[review round N]` comments and the merge as the reviewer, each command picking its account with `GH_TOKEN=$(gh auth token -u <login>)` - never `gh auth switch`, which flips the account under every other session. A login gh cannot give a token for is a stop, since an empty `GH_TOKEN` silently falls back to the active account. Unset, or one login twice, keeps one account. Orca cannot wake the writer, so the rule forbids ending the turn while the review is open and the writer polls the PR for the next review comment, stopping when the reviewer task ends with no new comment or after 30 minutes - a dead or silent reviewer counts as not clean. In a workflow step that wait is foreground loops or across steps (`workflowPrompt`), since a background loop dies with the step. Real findings are fixed, the checks re-run, the same reviewer re-reads; only correctness/regression/test/doc findings block, at most 3 rounds, and a review that will not come clean leaves the PR open unmerged (the inner child ends `RESULT: not fixed`). CI (typecheck + tests on ubuntu, Bun pinned to the host's version) runs on every PR and push to main. The repo is private on a free plan, so GitHub refuses branch protection and rulesets (403): `merge-when-green.sh <pr>` is the gate instead, run from the worktree: it waits until the PR head IS the local `HEAD`, until the CI check itself (`REQUIRED_CHECK`, `checks`) appears - GitGuardian passes in a second and would otherwise look like a green PR before Actions registered - and until nothing is pending, then merges with `--match-head-commit`, so a push landing meanwhile is never merged unchecked. A failed or cancelled check refuses (exit 1); its default 540s wait stays under the 10 min ceiling of a foreground tool call, and exit 3 means not finished yet, run it again. The ORCA line in `personality.ts` names the reviewer as one of its Orca workers, with no Agent-tool exception left. The reply says what the reviewer found. Applies to developer sessions on this repo too.
- **A cold session must still see the message it is answering** (`buildContextWindow`, `domain/conversation.ts`): a session dropped by a prompt-fingerprint change (every restart that ships a rule change) reopens cold on a window of `DEFAULT_CONTEXT_WINDOW` (20) turns. The window kept the root plus EVERY attachment turn oldest-first before any recent turn, so a long thread with 25 screenshots filled all 20 slots with them and the newest message fell out: asked to hide the table of contents, the fresh session answered the thread's opening request with a summary of work done hours earlier. - **Workflows** (`application/workflow.ts`, `db/workflowRepo.ts`) bind a Slack thread to a durable CLI session: the first turn passes `--session-id <uuid>`, every later turn `--resume <uuid>`, so the model keeps its context and files. `respond` routes plain messages in a workflow thread to the workflow's front (below), never to the chat brain. `executer`+ only. **Auto-continue** (`domain/workflowContinue.ts`, `application/workflowContinue.ts`, migration v20): a workflow used to advance only when a human spoke - one posted "next update when the PR is opened" and sat idle 10.5 hours. The prompt now asks for one meaningful step per turn and a final `[continue]` line when work remains and it is not asking, blocked or done; the marker is stripped (from the live stream too) and the next step (`carry on with the next step of the task`) is queued after `CONTINUE_DELAY_MS` (5s, so a human message typed meanwhile goes first) through `runTurn` - the ordinary respond path, same queue/session/role checks, as whoever drove the last turn. A steer (see the front/worker split below) resets the count; `continue_seq` guards stale timers. After `AUTO_CONTINUE_CAP` (30) steps alone it posts one paused line. Stopped workflows and aborted turns never continue. A failed worker step (timeout, crash: `afterFailedStep`, called from `respond`'s catch for `autoContinue` turns) used to end silently with its steers stranded on the row - a 15 min timeout once left 5 queued notes unseen. Now it posts a `failedStepNotice` and retries once (`FAILED_STEP_RETRIES`, step told `RETRY_MESSAGE`, steers ride along since they are only dropped after a step ran); a second failure in a row (`stepFailures`, in-memory map wired at the root, cleared by any clean step) posts that it stopped and waits for a human, steers kept. The pending step (`continue_as`) is on the row, so a restart between steps re-kicks it at boot (`resumeContinues`); a step already running when the process dies is not resumed. **Front/worker split** (`domain/workflowFront.ts`, `application/workflowFront.ts`, `runFrontTurn` in `application/workflow.ts`, migration v21): with auto-continue a human message still queued behind the running step on the same session, so "status?" waited minutes. Now the worker (`workflow.sessionId`, steps only - `autoContinue` turns and the command's first step, which takes the queue and is tracked too) runs on the thread key `${channel}:${threadTs}`, and every human message in a workflow thread runs on `frontKeyOf(key)` (`…:front`) against the front's own session (`front_session_id`, claimed only after its first turn finishes). The front gets a digest built at turn time (`frontDigest`: worker running/queued/idle and since when from the run registry + queue, the last 3 worker replies kept on the row in `worker_replies`, and the last 15 worker tool calls read back from the per-thread trace by `readTraceCalls`, filtered to `run: "workflow"` - the front bills as `workflow-front` so its own calls stay out), read-only tools (`PAL_TOOLS`, no skip-permissions) and a 4 min timeout (`FRONT_TIMEOUT_MS`). Lines `[steer] <instruction>` in its reply are stripped (live stream too, `createSteerFilter`) and stored on the row (`steers`, JSON); the worker's next step message carries them (`steeredMessage`: "Name (<@id>) said mid-task: ...") and clears them only after the step ran. A steer resets the auto count; if the worker is idle (no run/queue on its key and no `continue_as`) `steerWorker` requests and kicks a step at once as the steerer, and steers that arrived mid-step force one more step in `afterWorkflowTurn` even without `[continue]`. Steers survive a restart (`resumeContinues` kicks a step for them). `workflow stop` stops both keys' runs and clears steers; `workflow stop <thread-link>` does the same for another thread's workflow and posts nothing there (quiet only in that form, via a per-call `quiet` predicate on `CommandDef`; stopping 13 old workflows with `tell` once left an echo and a reply in every thread); the `stop` command and Slack's stop button reach the worker key (the button stops the front too). Limitation: a steer lands at the next step boundary, never mid-step. **Agents in a workflow** (`workflowPrompt`): the worker prompt carries `ORCA_AGENT_RULES`, so a worker that fans out starts Orca workers, never the Agent or Workflow tool, and waits for its batch across steps (done check at the start of the next step, other work or a foreground loop of up to 5 min if not done) - never a watch, since that turn lands on the front, and never bare check steps, which burn `AUTO_CONTINUE_CAP`. Below-executer users in a workflow thread still get ordinary chat, on the front key.
- **The brain can run commands** for anyone it is talking to: `bin/jarvis-run.sh` posts to `POST /api/commands/run` on the loopback dashboard, which the composition root wires to `dispatchCommand`. The request carries a **ticket**, never an actor - `application/commandTickets.ts` mints one per turn bound to the current speaker, so a sandboxed session cannot name someone else and escalate. The command's own `minRole` still gates what runs. The ticket reaches the CLI through its **environment** (`JARVIS_RUN_TICKET`), never its prompt: a thread holds one long-lived session, so every prompt it was ever handed is still in context, and a printed ticket is one the model eventually retypes from memory - expired by then (TTL, uses, or a restart), which bricked command-running for a whole thread, and belonging to whoever was speaking at the time, which is the escalation the ticket exists to prevent. The use budget (`COMMAND_TICKET_USES`, default **50**) is a RUNAWAY GUARD, not a rate limit, and it was 5 - which is neither. Asked to delete 26 messages the bot managed five, was told only "that ticket is not valid any more", guessed at the cap twice and got it wrong both times, asked the user to keep pinging it five at a time, and finally offered to bypass `rm-msg` with a raw `chat.delete` - the exact escalation the ticket mechanism exists to prevent. A guard that stops ordinary work becomes pressure to work around it. So: the number is high enough that only a loop reaches it, a spent ticket reports `spent` rather than looking indistinguishable from an expired one, and the turn is TOLD its budget up front (`commandBudget` in the prompt) so it plans and loops instead of discovering a wall halfway. Bulk work is an ordinary shell loop over the helper - every iteration spends one use, so looping never dodged the cap and raising it was the only fix. The helper drops a leading ticket-shaped argument so a session remembering the old signature still works.

- **Self-update** (`domain/selfUpdate.ts`, `bin/jarvis-restart.sh`, `POST /api/restart`): a full-access turn could always edit this repo and run the suite; what it lacked was a safe way to finish - `launchctl kickstart` from inside a turn kills the turn that asked for it. Admin+ only (`canTeach`), and a role that may not do it is not even shown the block. **Draining, bounded** (`onDrain`/`onForce`/`RESTART_MAX_WAIT_MS`, `cut_at` on inbox rows): waiting for "idle" with no bound meant several busy threads could hold a restart forever, every thread paying for the slowest. Now the moment a restart is asked for, the receiver stops claiming (`pauseIntake`, the gateway keeps queueing), the watcher/inner child/review inbox ticks hold (reminders still post, they start no turn) and `kickContinue` leaves a due workflow step on its row (`deps.draining`) for `resumeContinues` in the next process. Turns that are not inbox rows (watch-fired, inner child fixes, a running workflow step) die with the process on a forced exit - launchd kills the job's process group - and are not resumed; `docs/rolling-restart.md` is the plan for that.

- **Credential gap - ONE rule** (`domain/credentialGap.ts`): a chat turn runs on a setup token with zero `mcp__` tools, so "it is private", a 403, an empty page, `channel_not_found` and a missing tool ALL mean the same thing - wrong credential for this turn - and the fix is always to run a host-login command (`read`, `investigate`, `ticket`) itself through the run helper. Owner-only was the original call and made the command useless for the case it exists for - a colleague asking it to follow a team document - so the threshold is the instance owner's decision, not a constant. A refusal names who CAN run it rather than just saying no. The brain writes a file, then `note <file> [title]` publishes it and hands back the url. - **`note` UPDATES as well as creates** (`domain/noteTarget.ts`, the three modes in `notePrompt`): it could only ever create, and that was in the prompt in those words - "do not edit, move or delete any page that already exists". It was the narrow safe thing to build first, and it turned into the complaint: asked to update a document, it published a second copy, so a team ended up with two runbooks and no way to tell which was real. A document that silently forks is worse than one nobody can edit. `note <file> <notion-url>` (or `--into`) replaces that page's body, `--append` adds to the end, and a bare file still just creates. The mode is CHOSEN, never inferred - editing the wrong page is the one thing worse than refusing to edit - and each mode forbids the others: a create may not touch an existing page, and an update may not create one when its target cannot be reached, which is the exact fallback that produced the duplicates. A replace reads the page BEFORE writing, so it can report what it replaced and notice a wrong target, and it is told not to quietly merge what the document leaves out but to say so instead. An update needs no configured parent, since it already knows where it is going. `credentialGap`'s entry for `note` says all this too, because the chat brain's only knowledge of what the command can do comes from there - a capability the brain is not told about is one it will not use.

- **Memory is a Hermit adapter, not a table** (`domain/adapter.ts`, `domain/adapterCheck.ts`, `infrastructure/adapter/adapterStore.ts`, `adapter_files`): memory used to be a `learnings` table whose every row rendered into every prompt, in every channel, forever. 25 rows, 4.2KB a turn, and because nothing ever read it back as a whole it held a fact and its own retraction at once (`sql-runner is not used for preprod` directly above `Correction: ... DOES support SG preprod`), two unmerged wordings of one instruction, and a dozen repo facts loading into conversations about lunch. It is now a directory in the shape [Hermit](https://github.com/Infini-AI-Lab/hermit) uses for a harness adapter, `H = (p, G, K, M)`: `ADAPTER.md` is the policy (rules, always on), `memory/NOTES.md` the global notes, `memory/people/<SLACKID>.md` and `memory/channels/<CHANNELID>.md` load ONLY when that person is present or in that channel, and `skills/<slug>/SKILL.md` carries depth with only its `description:` always-on. The filename IS the lookup key, so a scoped note named anything but an id would never load and the gate refuses it. The format is borrowed rather than invented so the framework's own tooling reads the same directory - verified: `hermit.adapter.loader.load_manifest` accepts it. The bot does NOT use `hermit deploy`: that writes `CLAUDE.md` into a workspace, and the bot's CLI runs under an identity lock that ignores CLAUDE.md, so a deployed file would reach nothing. The rendered context goes through `--append-system-prompt` instead, which is the channel that actually arrives. With no adapter at all the bot uses the flat list unchanged, so an un-migrated instance keeps working.
- **The adapter lives in the database; the folder is a mirror** (`adapter_files`, migration v22, `adapterStore.ts`): it used to be the `data/adapter/` directory, written by the bot and committed by hand, so git held a copy that drifted from what the bot knew and read like stale memory left behind. Now one row per file is the truth, and every write re-renders `ADAPTER_PATH` (default `data/adapter-mirror`, gitignored) because skills are read by path and `browser-ui-test` ships scripts run by path. The mirror is output only - a start or a write overwrites any edit made there. To change a skill by hand: `adapter export` (a temp copy), edit it, `adapter import <dir>`, or edit the file in the dashboard's Memory page - same gate and revision log as a refine pass. `data/adapter/` is imported once, only while the table is empty.
- **There is ONE store of memory, and the fallback is the last good read** (`createAdapterReader`): `adapter migrate` empties the `learnings` table it copied from, and the revision it writes is the record of what was there. Leaving the table populated "as a fallback" was the first instinct and it is wrong twice over - it restores the PRE-curation list, contradictions and all, and it goes staler every day while looking authoritative, which is the exact class of silent-wrong-answer this whole area keeps producing. Two stores means one of them is lying. So when a manifest stops parsing the reader serves the LAST GOOD READ instead: the real memory, minus whatever broke it, logged loudly. With the table empty the dashboard overview counts memory items instead, and the Learnings page becomes a Memory page. Its writes are teach, revert, and a hand editor (`editAdapterFile`, `GET /api/adapter/files`, `POST /api/adapter/file`) that rewrites ONE whole file per save through `commitAdapter` - the same gate as refine, recorded as a revision (`edit <path> by hand`, by `dashboard`), allowed over the always-on budget with a warning like teaching, blank content removes the file (never `adapter.yaml`), and only canonical paths are taken (no `.`, `..` or empty segment, no leading `/`, no backslash) since `a/./b` is a second store row writing the same mirror file, and a path differing from an existing one only in case is refused for the same reason on macOS's case-insensitive disk. Each save carries `base`, the text the editor was opened on, and is refused when the stored file moved since - otherwise a save from a page left open silently undoes a fact the bot learned meanwhile. `commitAdapter` checks a proposal against the manifest it CARRIES, not the live one (and loads the live one only for `enforceFixed`, so a broken live manifest can still be repaired), so a manifest edit that narrows `learnable` under files already there is refused instead of leaving every later `learn` refused. The owner asked for it to fix notes by hand. What stays gone is the old grid of per-fact text boxes writing straight into an unchecked list, which is how that list came to hold a fact and its own retraction at once.
- **The always-on budget is the rule that matters** (`ALWAYS_ON_BUDGET`, `ADAPTER_BUDGET`, default 8000 bytes): Hermit caps each file, which stops any one of them running away - but what actually went wrong was the TOTAL, growing one line at a time with nothing ever taking a line out, and no per-file cap would ever have caught that. So the budget is on what loads unconditionally (policy + global notes + the skill index). It is deliberately asymmetric: a `learn` may exceed it and is TOLD so, a refine pass must come in under it. Teaching has to stay instant and unrefusable - the moment "remember this" can fail, people stop telling the bot things - while getting back under the line is precisely what curation is for. A refine gets under it by scoping a note or promoting it to a skill, NEVER by dropping one.
- **Curation is a separate act from learning** (`domain/refinePrompt.ts`, `adapter refine`): `learn` appends under a `## Recently taught` heading and a refine pass files it - merges duplicates, resolves a `Correction:` pair into one plain statement, scopes person/channel facts to their files, promotes procedural and repo-shaped knowledge into skills, retires only what is superseded or dead. It runs against a STAGING COPY: the model edits a throwaway tree, and the command puts what comes back through the gate before committing it. The thing that might lose something cannot also be the thing that decides the write was fine. `enforceFixed` stops a pass rewriting `adapter.yaml` - the manifest declares the very limits it is checked against, so a proposal that may edit it can lift them.
- **Every change to memory is a revision** (`db/adapterRevisionRepo.ts`, migration v11): a whole snapshot per commit, not a diff - an adapter is a few dozen small text files and a revert that cannot itself fail is worth more than the bytes. `adapter history` / `adapter revert <id>`. A bad refine is noticed days later, which is exactly when a diff-based history is least useful.
- **The adapter's policy is in the session fingerprint; its notes are not** (`promptFingerprint`): the policy and skill index are rules - they change behaviour everywhere - so changing them abandons running sessions, the same way an edited persona does. Notes are additive and taught often; hashing them would reset every open thread the moment anybody said "remember this". Same line that was already drawn for `learnings`.
- **`check.py` mirrors `adapterCheck.ts` on purpose**: two implementations of one contract is a liability, so the split is sharp - `adapter.yaml` declares the per-file limits and BOTH sides read them from there. Only what the manifest cannot express is hardcoded in each: the always-on budget, and the Slack-id filename rule. Keep `ALWAYS_ON_BUDGET` in the two files and `ADAPTER_BUDGET` in the env in step.
- **A prompt change does NOT reach a live thread** (`domain/promptFingerprint.ts`, `thread_sessions.prompt_hash`, migration v10): the system prompt is passed on every run, but a resumed session carries everything it has already said and that wins. One language rule was "fixed" three times - correct prompt, passing tests, unchanged behaviour - because the thread kept resuming a session opened under the old rules. Each session now records a fingerprint of the rules it was opened under (persona + every rule block, rendered with fixed sentinels; learnings and per-turn context deliberately excluded), and a session whose fingerprint no longer matches is dropped and reopened cold. When debugging "the prompt says X but it does Y", check `thread_sessions` before touching the prompt again.
- **Being asked for the raw path is an instruction, not a loophole** (`commandRules`): "do NOT reimplement what a command does" was written to stop the bot quietly substituting its own version, and it hardened into a flat refusal. Asked by the OWNER for 23 reactions explicitly not via `bomb`, it refused, refused again on the second ask, suggested the rule be edited in its source - and then refused to make that edit when asked. The rule's own stated reasons were already satisfied: `bomb` is admin and the asker was owner, so the role check and the allowance were never in question and only the audit log was at stake. The rule now turns on the ROLE, not on whether it was asked: if the person could have run the command themselves, do what they asked and say in one line what it skips; if they could not, refuse and name who can - that is the escalation it was always about. It also forbids meeting a second ask with the same refusal, and forbids offering "edit the rule in my source and I'll comply", which invites someone to rewrite your instructions to get an answer you could have given.
- **A rule written to fix one direction teaches only that direction**: the language rule was written after "Vietnamese in an English thread" was reported three times, and it illustrated exactly that case - "if it is in English, answer in English even for the line where you are addressing someone you usually speak another language with". Both the code rule AND the DB persona carried the same one-sided example. So in an all-Vietnamese thread, asked to explain something to a colleague, it answered in English - and the session was healthy, resumed, fingerprint current, with the Vietnamese context in its own memory. Nothing was stale; the rule simply never said the other direction existed, and a one-sided example reads as a preference. Both now state it BOTH ways and name the actual mistake: switching because of WHO you are addressing, whichever way it points. When writing a rule from one incident, check whether the mirror case is now implicitly endorsed.
- **Prompt layering - where a rule must live**: `buildSystemPrompt` uses the DB persona as `base` and falls back to `DEFAULT_PERSONALITY` only when none is set. Every real instance sets one, so a behavioural rule written into `DEFAULT_PERSONALITY` is DEAD CODE in production - that is exactly how a language fix shipped, tested and changed nothing. Anything that must always hold goes in `OPERATING_RULES` ("always apply, regardless of anything above"), which is appended after the persona. Check for a contradicting line in the DB persona too: the two compete, and the persona usually wins.
- **A streamed message dies at 12,000 characters** (`STREAM_CHAR_BUDGET` in `slack/stream.ts`): measured, not guessed - appending 2,000 at a time succeeded through 10,005 and the next chunk failed with `msg_too_long`, and so did `stop`. It is not a truncation, it is a LOSS: the append throws, the stream breaks, and an answer that took minutes to produce never arrives. `msg_too_long` is in this instance's log dozens of times. So a long reply rolls over into a continuation message at 11,000 (headroom, because task cards share the allowance), verified end to end against the real API: 20,000 characters now arrive as two messages with nothing dropped. The cut lands on a word boundary (`rolloverCut`: after the last line break, else the last space, else roll over first and only hard-cut a fresh message) - a cut at the exact budget once split "restart o" / "nce idle" across two messages, in a SHORT reply whose message was already full of task cards.

That is where a busy thread collected a row of placeholder cards that never completed. Every exit path now finishes or abandons the stream, `finish()` is called whether or not it `started` (an unfired timer is still armed), and a card left with no real content behind it is removed.
- **Slack output** (`domain/slackFormat.ts`): `SLACK_FORMAT` + `SLACK_BREVITY` are shared by the chat prompt, `ticketPrompt` and `reviewPrompt`'s close-out. - **Block Kit in a reply** (`domain/blockKit.ts`, wired in `slack/stream.ts`, `slack/app.ts` say, `adminClient.post`): the model marks rich content with a fenced code block tagged `blockkit` holding a JSON array of blocks, and the extractor lifts each one out of the text as it streams, so the stream sends the prose as `markdown_text` and the fence as a `blocks` chunk IN PLACE (Slack added `blocks` chunks to `chat.appendStream` in 2026-04). The plain post path wraps the prose in `markdown` blocks around them, keeping the prose as the `text` fallback. A fence that does not parse is shown as code, never dropped. Ordinary code fences pass through untouched, and the extractor gives identical output however the deltas are chopped (tested at 1-13 char slices).
- **`sys` reports the host, and leads with a verdict** (`domain/systemStatus.ts`, `infrastructure/system/systemProbe.ts`): "what is the RAM and CPU" is never the real question - the real one is "is anything wrong" - so a reading is classified ok/watch/problem with reasons, and the numbers come after. Load is judged PER CORE (12 on 10 cores is busy, 12 on 2 is a problem; the raw figure cannot tell those apart). The memory figure is the trap: `os.freemem()` is the kernel's free-page count, which on macOS reads ~2GB of 32 on a perfectly healthy machine because cached pages are not "free" - report that and every check looks like an emergency. The probe uses `memory_pressure` on macOS and `MemAvailable` on Linux, and `memSource` records which it got so a reading taken the unreliable way SAYS so instead of quietly lying. - **`help` is a menu, not a list** (`domain/commandMenu.ts`, `postMenu` on `SlackAdminPort`): forty lines of `- \`name <args>\` - summary` were always discoverable and never convenient - read, scroll back, retype with the prefix, get the argument shape slightly wrong, and on a phone it is genuinely unpleasant. The list stays because it is what you read to find out what exists, to copy a command into a script, or to check an argument shape without opening a modal - replacing it with a picker traded one awkwardness for another. Every button in one block needs a DISTINCT `action_id` - a row sharing one is rejected with `invalid_blocks` at post time, which would only surface the first time somebody pressed it - so the command goes in the id and the handler matches `MENU_RUN_PATTERN`. A `destructive` command (`forget`, which wipes a channel's turns) is never a button, because a button is one stray tap, and is confirmed in a modal when picked. The plain list stays the fallback for the dashboard, tests, or a failed post - help that fails is worse than help that is old-fashioned.
- **A guess is answered, not refused** (`domain/commandSuggest.ts`, `domain/commandHelp.ts`, `dispatchCommand`): the command log is a list of people who knew what they wanted and were told `I do not recognise X. Try help.` - `hel[`, `bomp`, `approvel`, `who` for `whoami`, `learns` for `learn`, and a bare PR url typed five times by someone who meant "review this". A near miss now NAMES the near match, drawn only from commands the asker's role can actually run, so a suggestion is never a door that turns out to be locked; the tolerance scales with length, because two edits from a three-letter name is a different command, not a slip. A line whose first word is a PR url routes to `review` with the whole line as its arguments. Commands that answer `help` better themselves set `ownHelp`. A killed command now says it ran past its time limit rather than `That command failed: claude CLI exited with code 143: no output`, which reads as a bug and invites the same expensive question again.
- **`approve` exists because people kept typing it** (`approve <pr-url>`): five attempts in the log, one of them `approvel without review please`. It is not a new power - `review` approves up front, in code, before the brain is spawned - it is that same step with the review left off, and it refuses exactly where `review` refuses: a repository set to `approve-after` is an admin's decision about that repository and no role goes round it. No brain, so no Claude token and no cost; the pal allowance is what bounds it, which is also what makes it auditable, since every approval is a row in the command log against whoever asked. It says in one line what it did NOT do, because an approval with no review behind it deserves more than a silent green tick.
- **What it costs is recorded** (`llm_usage`, migration v12, `db/usageRepo.ts`, `domain/spendReport.ts`, `spend` command, `/api/usage` + the Spend page): every turn spawns a CLI process and a review runs for ten minutes, and nothing anywhere recorded what any of it came to - not per person, not per command, not in total. The adapter REPORTS through an `onUsage` sink and the composition root owns the database, so the port stays a port. `bill` on `LlmCompleteParams` carries who asked and what for; a run that cannot say whose it is is recorded as unattributed rather than dropped, because a breakdown whose total does not add up is worth nothing. The figure is LIST price: on a subscription credential nobody is invoiced it, so every place it is shown says so, because "we spent $48 yesterday" and "we consumed $48 of list-price model time" are different conversations.
- **A streamed message's `text` is not what it said** (`domain/slackMessageText.ts`): Slack stores a flattened fallback for a blocks message, and for a streamed reply that fallback runs the `task_card` titles together with the answer - so reading one back begins `🐦‍🔥 run: cd /repo && sqlite3 ...` before a word of the reply. - **`mindful` is the one place that knows what is going on** (`domain/mindful.ts`, `db/turnLogRepo.ts`, migration v13, admin+): every piece of this existed and none of it was together. The run registry knew what was in flight, but only so it could be stopped. `llm_usage` knew what things cost. Workflows knew what was open. - **A turn cannot wait, so the waiting is stored instead** (`domain/watch.ts`, `application/watcher.ts`, `db/watchRepo.ts`, migration v14, `watch` command, admin+): told to promote once an image build finished, it ended its turn with "Image build is still running, waiting on it before promoting" - and that was that. The turn was over, nothing was waiting, and the thread sat there until a person came back and prodded it. Not an error, not a timeout: a promise nobody was around to keep, which is the most annoying thing it does. Sleeping inside the turn is wrong twice - it burns the turn's own `CLAUDE_TIMEOUT_MS`, and the thread queue runs one turn at a time so a sleeping turn is a thread nobody can talk to. A watch is a row: a shell predicate polled on a timer OUTSIDE any turn or session (no model, no tokens, no queue slot), and when it finally exits 0 the thread is handed a fresh turn carrying the note the first turn left for itself. `--every` is floored at 15s and `--until` capped at 6h, because a watch nobody ends is a leak with a timer. Every ending posts - fired, expired, or the check kept failing to run - since a watch that stopped quietly would be the same broken promise it exists to fix. Exit 127 is told apart from a plain "not yet": a missing command is a broken watch, not a no. The tick is guarded against overlap, since two ticks on one due row would fire it twice. The hand-back turn is started, never awaited: the row is settled first, so it cannot fire twice, and a tick that waited on a half-hour turn left every other due watch unchecked that long (a restart's hand-back held a restart-confirm watch at 0 checks). A turn that fails to start still posts its line in the thread. Watches are durable on purpose and reloaded at boot. The prompt rule (`commandRules`, only when `canWatch`) is the half that actually changes behaviour: the moment it catches itself about to say it is waiting, it sets one - and when handed the thread back it is told to finish the job, not start it over.
- **Named waits, because inventing a predicate under pressure is how it does not get set** (`builtinCheck`, `bin/slack-wait.sh`): everything below was reachable with a hand-written `-- <shell>`, and that was the problem - the turn had to compose a correct shell predicate at exactly the moment it was already trying to wind down, so it usually just said it was waiting instead. A named kind is one word and the same command every time: `watch pr <url>` (merged), `watch checks <url>` (CI stopped being pending), `watch reply <thread-link> [from <@u>]` (somebody answered), `watch url <url>` (it responds). `pr` and `checks` cover the work it CREATED; `reply` covers an answer it is owed by a person, another agent or a build bot, which is the one it could not do at all before. Exit codes are measured, not guessed: `gh pr checks` is 8 while pending, 1 on failure, 0 when green, so CI waits for "not 8" - a failed build is an answer, and a watch that only fired on success would sit to its deadline on the day somebody most needs to hear. Targets are refused when they are not what the kind needs, and every target is single-quoted into the predicate so a url with `&` cannot become a second command. A named kind is only recognised as the FIRST word, so "tell me when the pr lands" stays a sentence. All four were run against the real services before shipping, not just unit-tested.
- **Waiting is a note, not a mode**: a watch holds no turn, no session and no queue slot, so the thread stays completely live while one is pending - people keep talking and it keeps answering, and the watch arrives as a new turn whenever it comes good. Both are asserted in `respond.test.ts` rather than inferred from the wiring. The prompt half is the other failure: the turn that SET the watch was already trying to hand the work back ("anh promote giúp em", "tell me the right command and I'll run it"), and a hand-back forty minutes later is worse than one before the wait, because by then nobody is reading the thread. The escape hatch is deliberately one line - name what blocked you - and it is scoped to this case only; nothing here loosens the ordinary caution about a production deploy nobody has approved. The hand-back runs as the person who set the watch, so it used to look typed by them: fired mid-turn, it posted "still working on X - yours is next" to someone who had sent nothing. The watcher now passes `unprompted: true`, and `respond` skips `announceBusy` for it as it does for `autoContinue` (not reused here: that flag means "workflow step only" and drops the turn in a thread with no workflow). It still queues; it just does not announce itself.

The client also sets `rejectRateLimitedCalls`, since a 429 otherwise sleeps out `retry-after`, which the timeout does not cover. One failed cancel only logs, so the close still runs that tick. Notices are looked for in the last 50 messages, enough for a channel of its own. A host asleep for more than ~5 min gets a notice too - correctly, it is unreachable. Unset channel: no alarm. The lead must stay well over 5 min: in prod Slack posted notices it had answered ok to deleting once they were within a few minutes of due (observed with a 3 min lead, so the window is at least ~2 min; ~5 min is assumed, not documented - the docs only mention a 60s limit), so a 3 min lead posted a notice every minute while online. So the notice still posts ~10 min after the last heartbeat, but it can no longer be cancelled after ~5 min without a successful tick: that is how long a restart may take, and a 5-10 min outage still gets a notice after the host is back (closed on the next tick, its length counted to the close).
- **Draining for a restart is deaf, and must say so** (`domain/drainNotice.ts`, `draining` on `/health`, `background` runs): a restart waits for running turns and pauses the inbox so the wait can end. Nothing is lost - the rows stay in the gateway and the next process takes them - but from a thread, silence and death are identical. Asked a question and then `??`, `??`, `<@bot>???` into nothing, the owner reasonably filed it as a bug. Three things were wrong and all three are fixed: each waiting thread is listed ONCE (`onDeferred` on the inbox receiver peeks at what is waiting WITHOUT claiming it, so the rows still belong to the next process); `/health` reports `draining` and returns 503 instead of "listening, connected for 221m", which was the same lie the connection watchdog exists to stop arriving from the other side; and a turn in a workflow thread is marked `background` and no longer counts towards idleness, because a worker is cut and redelivered on the same session anyway, so waiting on one bought nothing and cost everybody else their replies for up to fifteen minutes. Only a person ASKING earns the notice: `envelopeThread` skips every subtype but `file_share` and `thread_broadcast`, because the bot's own `chat.update` arrives as a `message_changed` with its bot id nested in `event.message` and no top-level `thread_ts` - it slipped past the bot filter and posted the notice at the DM root. The notice is NOT posted into the waiting threads (in a channel or group DM it was noise for everyone else): it is ONE message in `DRAIN_NOTICE_CHANNEL` (#jarvis_logs) listing a permalink per waiting thread, and `onDeferred` hands over the whole list each time a new thread joins so `index.ts` edits that message with `chat.update`. `envelopeThread` reports a top-level message as its own thread (`ts`), so every entry has a link. Unset channel: nobody is told.
- **The inbox body is Bolt's event WRAPPER, not a `payload` envelope**: `{ type: "event_callback", event: {...} }`, with the event at the top level. Reading it as `body.payload.event` matches nothing and notifies nobody, silently - which is how the drain notice was first written and would have shipped looking perfectly fine. Checked against the gateway and the fixtures rather than assumed.
- **`RESTART_MAX_WAIT_MS` stays at 15 minutes** on purpose. Lowering it was the obvious reaction to the incident and the wrong one: what held the restart open was a BACKGROUND worker, and those no longer count at all, so what remains is a foreground turn somebody is waiting on - cutting one of those early is a worse trade than waiting. There is a test asserting the floor; it was telling the truth.

- **Commands** are a single registry in `src/application/commands.ts`, invoked as `<COMMAND_PREFIX> <cmd>`, the `<SLASH_COMMAND> <cmd>` slash, or legacy `!<cmd>`. Add a command = one entry; it gets role-gating, logging, and dashboard listing for free.
- **The bot's runtime ignores this CLAUDE.md** - the bot runs the CLI in a temp cwd with an identity-lock that ignores CLAUDE.md/memory. This file is for developer / Claude Code sessions editing the repo.

## Running instance / ops

- **CLI auth is explicit**, not ambient: `CLAUDE_CODE_OAUTH_TOKEN` in `.env` (from `claude setup-token`) is loaded by Bun into `process.env` and inherited by the spawned `claude`. Before this the bot relied on whoever was interactively logged in on the host, which fails silently whenever that session lapses.

- The bot runs under **launchd** (`~/Library/LaunchAgents/com.acme.jarvis.plist`), so it starts at login and is revived if it dies. Restart after a change with `launchctl kickstart -k gui/$UID/com.acme.jarvis`; `pkill` will NOT stop it (KeepAlive revives it in 15s) - use `launchctl bootout gui/$UID/com.acme.jarvis`. Output goes to `logs/jarvis.{out,err}.log`.
- **The pal/executer sandbox does not currently restrict tools.** Measured, not inferred (see the allow-list note above): with the exact flags a `pal` turn is spawned with, a bare shell command ran. Everyone below admin is on the allowlist for chat, so this is a live gap rather than a theoretical one - a `pal` turn can reach the shell on the host. The fix is not a one-liner: it needs `--permission-mode` investigating (a first probe of `manual` was inconclusive), or the sandbox rebuilt on `--disallowedTools`, which is the only lever shown to refuse anything. Until then treat `pal` as "can run commands on the host", not as "sandboxed".
- **An MCP server is configured for the BOT's environment, not for your shell.** The bot runs under launchd with `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` and nothing else. `npx` on this host exists only inside nvm (`~/.nvm/versions/node/<ver>/bin`), so a server configured as `"command": "npx"` - which is what the vendor's own README gives you - connects perfectly from an interactive shell and fails in the bot with `Executable not found in $PATH: npx`. Verified that way too: `claude mcp list` passed from a terminal while every turn was failing. The check that means anything is `env -i HOME=$HOME PATH=<the plist's PATH> claude -p ...` and actually calling the tool. Local servers use `/opt/homebrew/bin/bunx` (already on that PATH, and brew-pinned) rather than an absolute nvm path, which is version-scoped and would break silently at the next node upgrade - the same trap as the Accessibility grant following the `bun` binary.
- **The gateway is its own LaunchAgent** (`~/Library/LaunchAgents/com.acme.jarvis-gateway.plist`, `bun run src/gateway.ts`, logs in `logs/gateway.{out,err}.log`). Restarting the bot (`jarvis-restart.sh`, or kickstart `com.acme.jarvis`) leaves it alone and messages queue meanwhile. Restart the gateway itself only when `src/gateway.ts`, `slack/gateway.ts` or `inboxRepo.ts` change: `launchctl kickstart -k gui/$UID/com.acme.jarvis-gateway`. Inspect the queue with `sqlite3 data/inbox.db "select state, count(*) from inbox group by state"`.
- **Never restart while a turn is in flight**: check `pgrep -f "claude -p"` first, or a review/workflow mid-run is killed (exit 143).
- Commit or push only when asked. Do not commit secrets (`.env` is gitignored).

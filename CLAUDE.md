# CLAUDE.md

Guidance for working on this repo. Keep it accurate - update it when behavior, structure, or conventions change.

## What this is

A configurable Slack agent bot (Bun + TypeScript). Its "brain" is the local **Claude Code CLI** (default) or the Anthropic API. It has SQLite memory, an allowlist with roles, live streaming replies, a command registry, and a React admin dashboard. The code is **generic** - the running instance's identity (name, persona, prefixes, etc.) lives in the DB / env, never hardcoded.

## Commands

```bash
bun test              # full test suite (bun:test)
bun run typecheck     # tsc --noEmit  (root)
bun run build:web     # build the React dashboard (web/ -> web/dist)
bun start             # run the bot + dashboard
bun run setup         # install + build:web
```

Always run `bun run typecheck` AND `bun test` before considering a change done. The `web/` app has its own `tsconfig`/deps - typecheck it with `cd web && bunx tsc --noEmit` after touching it, and rebuild (`bun run build:web`) since the bot serves `web/dist`.

## Architecture (clean, layered - dependencies point inward)

- `src/domain` - pure logic, no I/O: `types`, `access` (roles), `conversation`, `mentions`, `personality`, `toolPolicy`, `reviewPrompt`, `emoji`, `slackLinks`
- `src/application` - use cases + ports: `ports` (`LlmPort`), `handleMessage`, `respond`, `commands` (registry), `botProfile`, `slackAdmin`, `draftReply`
- `src/infrastructure` - adapters: `db/*` (bun:sqlite repos + schema/migration), `llm/claudeCli` + `llm/anthropic`, `slack/app` + `slack/adminClient` + `slack/stream`, `dashboard/server`
- `src/config/env.ts` - zod-validated env, fails fast
- `src/index.ts` - the only composition root; wires everything
- `web/` - React 19 + Vite + React Router 7 dashboard (JSON API under `/api`)
- Full docs: `README.md`, `ARCHITECTURE.md`

## Conventions

- **TypeScript, functional style. No classes** - repos/adapters are factory functions returning a bag of functions. Do not introduce OOP.
- **Never use `any`.** Use precise types; `unknown` + narrowing at boundaries.
- Local imports use explicit `.ts` extensions (Bun style).
- Use `bun:sqlite`; SQL is parameterized (named/positional binds), never string-concatenated.
- Depend on ports (`LlmPort`, `SlackAdminPort`, injected clocks/deps), not concrete adapters, so use cases stay testable with fakes + `:memory:` sqlite.
- Keep changes small and focused; add/adjust tests with any behavior change (TDD).

## Key facts (non-obvious)

- **Identity is data, not code.** Bot name/persona/labels live in the DB `settings` table (seeded, editable from the dashboard). Command triggers (`COMMAND_PREFIX`, `SLASH_COMMAND`), model, cwd, owner id, etc. come from env. Do NOT hardcode instance-specific strings (bot name, command prefix, db filename) in `src/` - the code defaults are neutral (`Assistant`, `//bot`, `data/bot.db`) and each instance overrides via env + DB.
- **The DB is committed** (path from `DATABASE_PATH`) and carries the allowlist + identity. Conversation `messages` are cleared before committing; WAL sidecars are gitignored. After schema changes, migrations run via `PRAGMA user_version` in `db/schema.ts`.
- **`ALWAYS_DISALLOW`** (`domain/toolPolicy.ts`) is denied to every role including full access - `--disallowedTools` is honoured alongside `--dangerously-skip-permissions` (verified), so it is a real denial. It holds the Slack connector's **write** tools by name (`SLACK_CONNECTOR_WRITES`: send/schedule/draft/canvas) and CloudWatch. It used to ban the connector wholesale, which also refused the READS - and reading impersonates nobody; it is the only way to see a channel or group DM the bot was never invited to. Posting is the thing that arrives under the authorising human's name, so only that is denied.
- **Roles** (`src/domain/access.ts`, `toolPolicy.ts`): `pal` < `executer` < `admin` < `owner`. owner/admin run the CLI full-access; pal/executer are sandboxed (`--allowedTools` allow-list, no `--dangerously-skip-permissions`, fixed cwd). `review` is a preset that always runs full-access and writes to the PR.
- **Turn timeouts**: a chat turn is killed by `CLAUDE_TIMEOUT_MS` (this instance: 50 min; code default 120s), which surfaces as `claude CLI exited with code 143: no output`. `isTimeout()` tells that apart from a real failure so the thread says "ran past my time limit, narrow it or use `workflow`" instead of "I hit an error" - the generic apology reads as a bug and invites the same expensive question again. Investigation turns (gcx/VictoriaLogs loops) are what hit it.
- **UI access probe** (`domain/uiAccess.ts`, `infrastructure/system/uiAccessProbe.ts`): macOS Accessibility is granted against the *path* of the launching binary, so for this launchd agent it is the runtime (`/opt/homebrew/bin/bun`), not `claude` and not a terminal - and an interactive test passes while the bot still cannot, because the terminal has its own grant. Worse, a package upgrade moves the binary and the grant silently stops matching (bun is `brew pin`ned here for that reason). So it is probed with `AXIsProcessTrusted()` (~50ms, cached 5 min), logged at boot, and reported on `/health` as `ui`/`uiState`. NOT by scripting System Events, which was the first attempt and answers a different question - Apple Events/Automation, grantable while Accessibility is not - so it reported `allowed` while the real UI call was refused. Note the probe reports on the BOT process; the brain's UI actions run inside the spawned CLI, which the system may hold responsible instead, so a denial names both binary paths. It never touches `ok`: nothing core needs the UI, which is precisely why losing it goes unnoticed. A probe that fails for a non-permission reason reads `unknown`, never `denied`.
- **Connection watchdog** (`domain/connectionHealth.ts`, wired in `slack/app.ts`): Socket Mode goes deaf silently - process up, launchd happy, dashboard answering, no messages arriving. `KeepAlive` only revives a process that exits, so the app exits itself (`process.exit(1)`) when the socket has been away longer than `CONNECTION_GRACE_MS` (3 min). `reconnecting` counts as away: both real outages were spent entirely in reconnect attempts. `/health` reports the socket state and 503s when deaf, because "recent activity" cannot distinguish quiet from deaf - that mistake was made twice.
- **Stopping a turn** (`application/runRegistry.ts`, `domain/runControl.ts`): every chat/workflow turn is tracked with an `AbortController`; the signal reaches `claudeCli`, which kills the child (same kill as the timeout, so a stopped run surfaces as exit 143 and `respond` must check `signal.aborted` before reporting it as a timeout). The busy notice is now interactive - `STOP_ACTION` ends the running turn, `DROP_ACTION` takes the just-queued one back before it spawns - and `stop` does the same without a new message. `decideRunPress` holds the rule: your own turn, or admin. A button whose run already finished answers "gone" rather than erroring.
- **Thread queue** (`application/threadQueue.ts`, wired in `respond`): chat and workflow turns of one thread run strictly one at a time. Two messages minutes apart used to run concurrently and each complete the same task (two branches, two PRs) while both resumed the SAME session id from two processes. Commands are intentionally not queued (own process, own session). A failed turn never breaks the chain behind it; `depth()` lets the thread be told it is waiting.
- **Thread sessions** (`domain/threadSession.ts`, `db/threadSessionRepo.ts`): every Slack thread gets ONE CLI session - first turn `--session-id`, later turns `--resume` - so the model keeps its context between turns and a resumed turn is handed only `unseenTurns()` (everything said since its last turn), not the thread replayed. Keyed by (channel, thread, **tier**): full-access and sandboxed roles use different cwds and the CLI files a session under the cwd it ran in, so cross-tier resume is impossible anyway and sharing would leak a full-access session's reads to a pal. The session is claimed BEFORE the run, never after: a turn that dies is usually the long one, and leaving nothing bound makes the retry start cold and repeat the discovery that ran it out of time. `isMissingSession()` (`No conversation found with session ID`, verified against the CLI) means silently mint a new session and replay the thread cold; any other error still throws. Setting `thread_sessions=off` and the `session` command turn it off / reset one thread.
- **Workflows** (`application/workflow.ts`, `db/workflowRepo.ts`) bind a Slack thread to a durable CLI session: the first turn passes `--session-id <uuid>`, every later turn `--resume <uuid>`, so the model keeps its context and files. `respond` routes plain messages in a workflow thread to that session instead of the chat brain. `executer`+ only.
- **The brain can run commands** for anyone it is talking to: `bin/jarvis-run.sh` posts to `POST /api/commands/run` on the loopback dashboard, which the composition root wires to `dispatchCommand`. The request carries a **ticket**, never an actor - `application/commandTickets.ts` mints one per turn bound to the current speaker, so a sandboxed session cannot name someone else and escalate. The command's own `minRole` still gates what runs. The ticket reaches the CLI through its **environment** (`JARVIS_RUN_TICKET`), never its prompt: a thread holds one long-lived session, so every prompt it was ever handed is still in context, and a printed ticket is one the model eventually retypes from memory - expired by then (TTL, uses, or a restart), which bricked command-running for a whole thread, and belonging to whoever was speaking at the time, which is the escalation the ticket exists to prevent. The helper drops a leading ticket-shaped argument so a session remembering the old signature still works.
- **Investigation** (`domain/investigation.ts`): logs/metrics/traces come from Grafana via the `gcx` CLI first, Datadog second, and never CloudWatch (billed per GB). The order is a setting (`log_sources`, `logsource` command); the CloudWatch refusal is both a prompt rule and a `SANDBOX_DISALLOW` entry, since a full-access role cannot be denied anything.
- **Self-update** (`domain/selfUpdate.ts`, `bin/jarvis-restart.sh`, `POST /api/restart`): a full-access turn could always edit this repo and run the suite; what it lacked was a safe way to finish - `launchctl kickstart` from inside a turn kills the turn that asked for it. The helper runs `typecheck` + `bun test` and only then asks the RUNNING bot over loopback to exit after `RESTART_DELAY_MS` (6s), so the reply lands first and launchd brings it back. Both checks are a hard gate: restarting into code that does not compile is a crash-loop `KeepAlive` repeats every 15s, unfixable from Slack. Admin+ only (`canTeach`), and a role that may not do it is not even shown the block.
- **Slack reads for sandboxed roles** (`bin/slack-read.sh`, `domain/slackRead.ts`): a pal/executer has no `curl` on purpose - a general outbound request with `SLACK_BOT_TOKEN` in the env is an exfiltration channel - so a pal asking about a channel link got the tool policy's refusal reported back as "I do not have permission to read that channel", which was FALSE: the bot was a member and the same call succeeds. The helper is the narrow door (history/replies/info/user, read methods only, no posting), granted to every role like the react/file/grafana ones. A PUBLIC channel it has not joined is joined first (`channels:join`, announced on stderr - a join is visible to the channel); a PRIVATE one stays refused and is the host-login `read` command's job. The prompt rule ends with: never report a tool you were denied as a permission Slack refused you.
- **Credential gap - ONE rule** (`domain/credentialGap.ts`): a chat turn runs on a setup token with zero `mcp__` tools, so "it is private", a 403, an empty page, `channel_not_found` and a missing tool ALL mean the same thing - wrong credential for this turn - and the fix is always to run a host-login command (`read`, `investigate`, `ticket`) itself through the run helper. It also forbids the two things it actually did instead: grepping config files for API keys, and curling a private service's internal API then calling the empty body proof that a page is private. This replaced three near-identical rules (Datadog in `investigation.ts`, Slack then Notion in `readChatRules`) written one failure at a time - the same bug arrived three times because each rule described only its own case. `investigation.ts` now states only WHERE data lives; escalation belongs here.
- **`read` command** (`domain/readPrompt.ts`): reads anything the bot's own credentials cannot - a Notion page, a Slack channel/DM it was never invited to - through the account's connectors on the HOST login. Its role floor is a SETTING (`read_min_role`, default **admin**, `read access <role>` to change it, admin+ to set). Owner-only was the original call and made the command useless for the case it exists for - a colleague asking it to follow a team document - so the threshold is the instance owner's decision, not a constant. A refusal names who CAN run it rather than just saying no. It is a TOOL, not an errand (`quiet: true`): the run bridge gives it no `reply` and waits for it, so the content returns to the BRAIN and nothing is posted - one step inside a larger task. A person typing it still gets the answer in the thread, because `respond` wires `reply` for a message command. When it does report, it ANSWERS the question it was sent with - first line, then a handful of bullets, **fifteen lines maximum** - and never reproduces the source: it twice transcribed its input instead (a whole Notion ticket, then an entire ClickHouse handbook across three messages) while the actual answer sat in paragraph two. Reaching for a second message is the signal it stopped answering and started transcribing; it offers the rest instead. **Owner-only on purpose** - it reads with the authorising human's Slack access, so whoever runs it can read anything that person can. `readChatRules` is in the chat prompt so the brain escalates to it instead of answering "my rules forbid the connector", which was true of posting and wrong about reading. It never writes through the connector; the report comes back through the bot's own token, under its own name.
- **`investigate` command** (`domain/investigatePrompt.ts`): logs/RUM/traces investigation as a preset full-access task on the HOST login, for the same credential reason as tickets - Datadog is connector-only and a setup token loads zero `mcp__` tools, so a chat turn cannot see RUM at all. `investigation.ts` now tells the brain to RUN `<prefix> investigate` itself through the run helper rather than hunting for API keys (it went through `~/.claude.json` looking for Datadog credentials that do not exist) or asking the user to reconnect the connector - both of which it actually did. The prefix is substituted like the grafana helper path; with no prefix to name, the whole escape hatch is dropped rather than printing a placeholder. The prompt encodes the mistakes from the first real run: de-duplicate before counting (one crash emits ~4 RUM events), check every region not just the reporter's, prove the mechanism with a request timeline, and question an id that returns nothing rather than concluding there is no data.
- **Tickets run on the HOST login, not a token** (`useHostLogin` in `ports.ts` / `claudeCli.ts`): a `claude setup-token` credential carries NO claude.ai connector authorisation - under one the CLI loads **zero** `mcp__` tools (verified: same flags, same cwd, token set -> 0 tools; token unset -> Notion loads and reads the real tracker). So the setup-token migration silently removed every MCP connector from the bot, and `ticket` - the one feature that needs one - broke with it. There is no Notion credential of our own, so the ticket spawn DELETES `CLAUDE_CODE_OAUTH_TOKEN` from the child env (omitting it is not enough, the bot's own is in `process.env` and would win). Cost lands on whoever is signed in on the host, and `isAuthFailure()` names a lapsed session in the thread instead of "I could not raise that one". Everything else keeps the explicit token.
- **Tickets** (`domain/ticketPrompt.ts`): a preset full-access task like `review`. It reads the configured Notion SOP + pod pages + the tracker schema at run time and routes from those, so no pod, person or property name is ever hardcoded; settings are `ticket_tracker`, `ticket_sop`, `ticket_pods`, `ticket_repos`. `ticketChatRules` lets a bug reported in plain chat become a ticket. A PR is only opened for a small, verifiable fix, with a reviewer justified from CODEOWNERS/git history; `ticket_repos` accepts whole orgs as well as `owner/repo` (`parseRepoScope`), and an org grant makes the bot verify membership with `gh repo view` before pushing. A measured Risk section is added when the issue is not trivial.
- **Spoken review requests** (`domain/reviewRequest.ts`): a mention that says "review" and carries a PR url is routed to the `review` command by `respond`, not to the chat brain. Narrow on purpose (mention + the word + a real PR url) since a review spends the caller's own token - and only the command path can post the token button, so a spoken request otherwise got prose about the token instead of the box.
- **Per-user Claude tokens** (`domain/claudeToken.ts`, `application/claudeTokens.ts`, `db/claudeTokenRepo.ts`): a turn can run on the speaker's own `sk-ant-oat01-` token - `CLAUDE_CODE_OAUTH_TOKEN` in the spawn env overrides any login on the host (verified: a bogus value 401s even with a valid interactive session), so the usage is genuinely theirs. `review` REQUIRES one and refuses without it (no fallback to the bot's credential, ever - and the caller's token REPLACES it in the spawn env, so the bot's is not in that process at all); each person gets the full ask exactly once (`token_asks`, cleared when a token is set or removed); every other turn uses one when present and the bot's own otherwise. Tokens arrive only through a Slack modal (button -> `views.open` -> `view_submission`), never as a message, and the button's `private_metadata` carries the blocked command so submitting resumes it. Storage is a separate DB (`TOKEN_DATABASE_PATH`) encrypted under `TOKEN_KEY_PATH`; the key is gitignored, the DB is not.
- **Per-run review policy**: `review <url> --policy first|after|default` (also `--first`/`--after`, `--policy=x`, `policy:x`) overrides the repo's policy for one run without persisting it (`parsePolicyArg` in `domain/reviewPolicy.ts`, which also strips the flag so it reaches neither the url parser nor the steering note). Tightening is open to anyone; loosening an `approve-after` repo needs admin, since that repo's policy was an admin decision. An unparseable value is refused, never silently ignored.
- **Review comment shape** (`reviewPrompt.ts` step 4): a landing line then bullets, one issue each, worst first. Two standing rules - nothing already in the PR description/commits/comments is repeated (it reads them in step 1, before reviewing), and anything the author declared out of scope gets ONE warning bullet naming the residual risk instead of being raised as a finding, never blocking. The carve-out: scope excuses what a PR does not fix, never what it breaks.
- **Review targets**: an argument must pass `looksLikePrRef` (url, `owner/repo#123`, or a bare number) before a review spawns - `review help` used to review a PR named "help" on the caller's token. `review help` / `review prompt` answer the question instead, the latter printing the real system prompt (clipped, since it is longer than one Slack message).
- **Review steering**: anything typed beside the url in `review` becomes a quoted note in the prompt (`steer()` in `reviewPrompt.ts`) that aims the review. It is user text, so it is scoped explicitly - it cannot skip a PR, waive a flow, invent an approval or change the house style, and a note asking for work outside a PR review is refused out loud in the close-out.
- **Review fan-out** (`domain/reviewPrompt.ts`): a big PR is cloned and reviewed by child agents, capped at `DEFAULT_REVIEW_AGENTS` (3), spawned in one batch, configurable via the `review_agents` setting / `review-agents` command (1-8, `asAgentCap` clamps). The prompt also forbids running commentary, forbids asking the user anything (it runs unattended, so a question is a finding left unposted - a late blocking finding from an agent that reported after the comment went up gets its own short follow-up comment instead), and tells the brain to drop a silent agent rather than wait out the budget - an unbounded fan-out plus "waiting on the agents" narration is what used to burn the whole `REVIEW_TIMEOUT_MS` with nothing posted. When the CLI is killed mid-run, `claudeCli.stream` emits `{type:"aborted"}` so the caller reports an unfinished run instead of presenting the fragment as the answer.
- **A prompt change does NOT reach a live thread** (`domain/promptFingerprint.ts`, `thread_sessions.prompt_hash`, migration v10): the system prompt is passed on every run, but a resumed session carries everything it has already said and that wins. One language rule was "fixed" three times - correct prompt, passing tests, unchanged behaviour - because the thread kept resuming a session opened under the old rules. Each session now records a fingerprint of the rules it was opened under (persona + every rule block, rendered with fixed sentinels; learnings and per-turn context deliberately excluded), and a session whose fingerprint no longer matches is dropped and reopened cold. When debugging "the prompt says X but it does Y", check `thread_sessions` before touching the prompt again.
- **Prompt layering - where a rule must live**: `buildSystemPrompt` uses the DB persona as `base` and falls back to `DEFAULT_PERSONALITY` only when none is set. Every real instance sets one, so a behavioural rule written into `DEFAULT_PERSONALITY` is DEAD CODE in production - that is exactly how a language fix shipped, tested and changed nothing. Anything that must always hold goes in `OPERATING_RULES` ("always apply, regardless of anything above"), which is appended after the persona. Check for a contradicting line in the DB persona too: the two compete, and the persona usually wins.
- **Slack output** (`domain/slackFormat.ts`): `SLACK_FORMAT` + `SLACK_BREVITY` are shared by the chat prompt, `ticketPrompt` and `reviewPrompt`'s close-out. The prompt rule is NOT enough on its own - models reach for Markdown anyway on long relayed answers - so `toMrkdwn()` converts at the posting boundary (`slack/app.ts` say, `adminClient` post/postDm/interactive blocks): `**b**`->`*b*`, `[l](u)`-><u|l>, `#` headings -> a bold line, `*`/`+` bullets -> `- `. It holds out fenced and inline code first (``**ptr`` is code, not emphasis) and leaves unpaired markers alone. The streaming path sends `markdown_text`, which Slack converts itself, so it is not double-converted. Slack is mrkdwn, not Markdown - `**bold**` and `[x](y)` render literally - so any new prompt that produces Slack text must include them.
- **Commands** are a single registry in `src/application/commands.ts`, invoked as `<COMMAND_PREFIX> <cmd>`, the `<SLASH_COMMAND> <cmd>` slash, or legacy `!<cmd>`. Add a command = one entry; it gets role-gating, logging, and dashboard listing for free.
- **The bot's runtime ignores this CLAUDE.md** - the bot runs the CLI in a temp cwd with an identity-lock that ignores CLAUDE.md/memory. This file is for developer / Claude Code sessions editing the repo.

## Running instance / ops

- **CLI auth is explicit**, not ambient: `CLAUDE_CODE_OAUTH_TOKEN` in `.env` (from `claude setup-token`) is loaded by Bun into `process.env` and inherited by the spawned `claude`. Before this the bot relied on whoever was interactively logged in on the host, which fails silently whenever that session lapses.

- The bot runs under **launchd** (`~/Library/LaunchAgents/com.acme.jarvis.plist`), so it starts at login and is revived if it dies. Restart after a change with `launchctl kickstart -k gui/$UID/com.acme.jarvis`; `pkill` will NOT stop it (KeepAlive revives it in 15s) - use `launchctl bootout gui/$UID/com.acme.jarvis`. Output goes to `logs/jarvis.{out,err}.log`.
- **Never restart while a turn is in flight**: check `pgrep -f "claude -p"` first, or a review/workflow mid-run is killed (exit 143).
- Commit or push only when asked. Do not commit secrets (`.env` is gitignored).
